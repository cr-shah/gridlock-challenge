# Codex prompt: build one safe, unified Gridlock project dataset

> **Superseded by the pipeline publisher.** The canonical implementation now lives in
> `gridlock-data-pipeline` and publishes `data/published/gridlock_master_projects.json` with
> `python -m gridlock_pipeline publish`. Do not use the older product-repository implementation
> prompt below for new work; it is retained only as historical handoff context.

This file is a handoff for a teammate. Copy the prompt below into Codex while working in the `gridlock-challenge` repository.

The central rule is simple: **unified does not mean that every record becomes verified**. The unified output must retain provenance and clearly distinguish official/verified geometry, estimated screening geometry, missing geometry, and demo-only records.

## What the existing files actually mean

| File | Meaning | Use as an input? |
|---|---|---|
| `data/verified_projects.json` | Canonical real DESC and GPC project catalog. Some projects have verified geometry; many have `null` geometry. | **Yes — primary source** |
| `data/estimated_geometry.json` | Geometry overlays for real projects that lack verified geometry, plus an unresolved list. | **Yes — geometry overlay only** |
| `data/projects.json` | Legacy/demo projects with placeholder coordinates. | **No — keep separate and labeled demo** |
| `data/analysis.json` | Generated scoring result from verified-only mode. It repeats project data and includes matches. | **No — generated output** |
| `data/estimated_analysis.json` | Generated scoring result after estimated geometry is applied. | **No — generated output** |
| `data/demo_analysis.json` | Generated scoring result for demo mode, including illustrative fields. | **No — generated output** |
| `data/product_schema.json` | Existing product-facing schema documentation. | **Yes — reference** |

Do not combine pair-level `matches`, rankings, coordination scores, or illustrative savings into the unified project catalog. Those are calculated outputs, not project source data.

## Copy/paste this prompt into Codex

```text
Work in the gridlock-challenge repository.

I need you to create a safe, derived unified project dataset because this repo currently contains verified source records, estimated geometry overlays, legacy demo records, and generated analysis files with different shapes.

GOAL

Create one canonical REAL-project dataset that contains every project from data/verified_projects.json exactly once and makes its geometry state explicit:

1. Use verified project fields from data/verified_projects.json as the base record.
2. If a base project already has usable geometry, preserve it byte-for-value and label its geometry origin VERIFIED.
3. If the base project has no usable geometry, look for its project_id in data/estimated_geometry.json and apply that geometry only as a derived overlay. Label its geometry origin ESTIMATED.
4. If neither verified nor estimated geometry exists, keep the project and label its geometry origin UNRESOLVED. Never drop it.
5. Never relabel estimated or demo geometry as verified.
6. Never infer or invent missing coordinates, dates, owners, voltage, confidence, or provenance.

SOURCE-OF-TRUTH RULES

- data/verified_projects.json is the only source of real project identity and project facts.
- data/estimated_geometry.json may add geometry-related fields only to a project with missing verified geometry.
- Match estimates to real projects only by exact project_id == id. Do not fuzzy-match names.
- Verified geometry always wins. An estimate must never replace or modify existing verified geometry.
- data/projects.json is legacy/demo only. Do not merge it into the real unified dataset.
- data/analysis.json, data/estimated_analysis.json, and data/demo_analysis.json are generated outputs. Do not use them as source inputs.
- Illustrative savings, coordination briefs, scores, closest points, tiers, and pair matches do not belong in the canonical project record.

IMPLEMENTATION

Create:
- scripts/build_unified_dataset.py
- data/unified_projects.json (generated by the script)
- tests/test_unified_dataset.py

Do not overwrite any existing JSON file.

The top-level output should be an object like:

NORMALIZATION RULES

- Keep geometry in GeoJSON coordinate order: longitude, latitude.
- Preserve Point, LineString, and MultiLineString without flattening or converting them.
- Do not round or simplify coordinates.
- Keep unknown values as null. Do not use empty strings, "unknown", zero, or fake defaults.
- Keep voltage_kv as an array. Do not convert it to a display string.
- Keep years as integer or null. Do not turn them into formatted labels.
- Preserve extra provenance fields from verified_projects.json when useful; do not discard information merely because it is not in the minimum shape above.
- For VERIFIED geometry, copy geometry fields from the base project and set unresolved_reason to null.
- For ESTIMATED geometry, copy only the estimate's geometry-related fields: geometry, geometry_type, geometry_method, geometry_confidence, geometry_source, geometry_notes, and tier_eligibility. Store tier_eligibility as geometry_tier_eligibility. Do not replace any non-geometry project fact.
- For UNRESOLVED geometry, keep geometry and its metadata null. Use the matching reason from estimated_geometry.json's unresolved list when present; otherwise use a neutral reason such as "No verified or estimated geometry available".

- Reject duplicate project ids with a clear error rather than silently choosing one.
- Reject duplicate estimate project_ids with a clear error.
- Ignore or report orphan estimates whose project_id does not exist in verified_projects.json; never create a new real project from an orphan estimate.

IMPORTANT SEMANTIC DISTINCTIONS

- data_confidence describes confidence in the underlying project record.
- geometry_confidence describes confidence in the geometry.
- geometry_origin says whether geometry came from the verified record, an estimated overlay, or is unresolved.
- These fields are different and must not be collapsed into one generic confidence field.
- A record can be a real/verified project while its geometry_origin is ESTIMATED or UNRESOLVED.
```

## Why this structure is safer

The real-project catalog and geometry quality are two separate ideas. A DESC project does not become a fake project merely because its route is unresolved, and an estimated route does not become official merely because it is attached to a real project. The `geometry_origin` field makes that distinction explicit for every downstream consumer.

The derived file should make application code simpler while preserving the original evidence chain:

```text
verified_projects.json ── base project facts ───────────────┐
                                                            ├── unified_projects.json
estimated_geometry.json ── missing-geometry overlay only ───┘

projects.json / demo_analysis.json ── remain separate demo data
analysis files ── remain generated pair/scoring outputs
```

If the website later consumes the unified file, that should be a separate task with its own tests. Building the unified dataset should not silently change scoring, Estimated Coverage, or the website.
